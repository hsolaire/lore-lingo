# 代码注释规范

## 语言要求

- 项目自有源代码、测试、脚本和数据库迁移中的自然语言注释必须使用简体中文。
- 新增或修改既有注释时，应将触及范围内的非简体中文说明统一为简体中文。
- 代码标识符、协议字段、命令、错误码、第三方 API 字面量、标准术语原文和许可证文本可以保留其规定语言。
- 第三方代码、自动生成文件和外部补丁不适用本规范；不得仅为翻译注释而修改这些文件。

## 分步骤注释

复杂且较长的逻辑必须使用连续的分步骤注释，固定格式为 `步骤 N. 简体中文说明`：

```ts
// 步骤 1. 校验输入和当前状态
// 步骤 2. 执行核心处理并保存阶段结果
// 步骤 3. 清理资源并返回最终结果
```

Rust、SQL 和其他语言应使用各自合法的注释符号，但步骤文字和编号格式保持一致：

```rust
// 步骤 1. 申请本次捕获所需资源
// 步骤 2. 执行捕获、识别和翻译流水线
// 步骤 3. 释放资源并映射最终状态
```

## 适用范围

出现以下任一情况时，应使用分步骤注释：

- 一个函数或代码块包含三个及以上具有先后依赖的处理阶段。
- 状态机、事务、异步并发、重试、回滚或错误恢复路径较复杂。
- 涉及资源申请与清理，例如窗口、监听器、工作线程、原生句柄、文件或数据库连接。
- 涉及捕获、OCR、翻译、字幕更新或持久化等跨模块流水线。
- 仅阅读局部代码时，难以快速判断执行顺序、关键不变量或失败后的恢复方式。

## 编写要求

- 步骤必须从 `步骤 1.` 开始连续编号，并紧邻对应的代码阶段。
- 注释应说明处理意图、顺序、关键不变量和恢复路径，不得逐行翻译代码语法。
- 当逻辑阶段发生增删或重排时，必须同步更新步骤编号和说明。
- 简单赋值、显而易见的条件判断和短小函数不需要步骤注释，避免制造噪声。
- `TODO`、`FIXME`、安全说明和兼容性说明也必须使用简体中文，并写清原因或后续动作。
